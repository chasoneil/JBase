## MQ

MQ message queue 消息队列，提供一种异步的通信方式，一般使用生产和消费的模型

好处：

* 异步
* 解耦
* 削峰填谷 

### 1. 常见MQ

* activemq 目前已经没人用了
* rabbitmq  erlang
  * 协议 ： AMQP advanced message queue protocol
  * 性能 单台 标准服务器 ： 1.2 并发
  * 支持非常多的语言
  * 支持持久化，但是开启持久化性能损失比较严重
  * 性能拓展性很差，集群化部署不能提高性能
* rocketmq  java
  * 协议 ： 自定义协议
  * 性能 ： 10万
  * 只支持Java
  * 支持持久化，性能损失很小 
* kafka  scala + java
  * 协议 ： 自定义协议
  * 性能 ： 百万
  * 支持多语言 
  * 支持持久化，性能损失很小
  * 对配置运维的要求很高
* pulsar



>  使用 MQ 的优缺点

优点：

* 异步、解耦、流量削峰
* 提高性能、 提高稳定性（避免单点故障）

缺点：

* 增加系统复杂度
* 受制于网络，所以最好是内网使用MQ

### 4. 消息不丢失

> RabbitMQ 

* 确保消息到 MQ exchange
* 确保消息路由到正确的队列

上面这两种可能是因为我们代码中写错了 routerKey , 这种情况下虽然生产者发送了消息，消息没有正确进入MQ

有可能是 没到 exchange 有可能是 exchange 没有正确的路由到 queue，当然也可能网络波动导致的

解决方案是 ： setPublicConfirm(true)  设置开启回调；setConfirmCallback(methodName) 设置回调的方法

在回调中通过 ack 判断消息是不是正确发送， 从而实现补偿机制或者其他：

1. 如果是超时，那么我们可以设置重发
2. 如果是路由失败，我们可以打开 setMandatory(true) 开启路由失败通知 setReturnCallback() 设置路由失败回调

* 消息在队列中丢失
  * 通过队列消息持久化解决，当然持久化必然会导致性能的下降
  * 同时交换器和绑定关系也要持久化
* 消费的过程中丢失消息
  * 消费的方法是 void 类型， 且是自动提交的，除了发生异常
  * 我们希望消费者自己控制，所以我们使用手动确认的方式；可以手动写一个监听的方法





> kafka && RocketMQ

* 保证消息到MQ
  * 发送的时候，尽量使用异步回调，使用ACK进行确认，同时重试机制

* 保证消息在MQ中不发生丢失

  * 将消息持久化 kafka 和 RocketMQ 都是持久化的

    * 消息到磁盘为了提高性能，一般都是异步 + 缓冲区的方式，但是异步 只是保证了数据到了内存，如果到内存断电了还是丢失

### 5. 消息顺序性

> Rabbit

*  queue 中只配置一个 exchange， 防止多exchange 将消息顺序打乱

> Rocket && Kafka

* 配置一个topic 下只有一个一个队列  可以保证全局顺序消息

  * 当一个topic 有多个queue的时候，因为消息会负载均衡会发送到多个queue中，消费者在消费多个queue

    自然是不保证顺序性的

* 当然我们可以通过 id 将指定的消息放到指定的queue中，那么就算有多个queue，每个queue中的顺序性还是

  有保证的，这个可以保证部分顺序消息

### 6. 消息不重复消费

MQ 自身是不能保证消息的不重复的，因为我们为了保证消息的不丢失，生产者可能会有重试机制，那么如果遇到网络问题

可能会出现重复消息。

解决方案：消费端做幂等性处理，有两种方案：

* MVCC 给消息加版本号  通过主键 + 版本号 ， 当对某个主键的值进行更改之后，版本号+1， 下次再去修改的时候，当遇到

  版本不一致的情况的时候就不执行了。

* 最常见的方案是去重表的方案 ： 使用MySQL中自定义的表 Unique id，或者内存中的Set， 去缓存一个id，当消费的时候，判断

  是不是重复的消息，如果是重复的，不进行后序的动作只是简单消费掉

### 7. 延时消息

延时消息：

 正常的消息，当生产者将消息丢给MQ, 消费者马上就可以消费，除非发生了消息堆积，不然一般延迟很低，

 与此相对的，延迟消息是在延迟一定的时间后才能被消费。

使用场景：

比如说买电影票，你选座之后，付款之前，座位会锁定，一般会给你15分钟时间付款，如果规定时间内没有付款，座位要释放

那么释放这个消息就要在15分钟后触发

支持的MQ:

* RabbitMQ

  * 使用死信消息队列和死信交换器，我们给消息设置一个死信时间，然后我们配置一个死信交换器exchange-dlx

    在感应到有死信消息的时候，该交换器可以将死信消息放到一个死信队列中，由专门的消费线程处理这些消息

* RocketMQ

  * 可以通过 message.setDelayTimeLevel(); 4.X版本开源版是不支持自定义时间的， 5.X可以自定义时间

### 8. MQ的设计

> Kafka 和 RocketMQ 的存储设计有什么不同

kafka 的存储是文件； kafka中最基础的概念是 topic, 底下是partition,  当然，虽然是partition但是我们其实可以将其理解成队列。

从broker的角度， 一个partition 对应一个文件。



RocketMQ 的设计和kafka不同， rocketMQ 中开始只有一个文件 CommitLog，所有生产者的消息都会首先进入这个文件，默认初始

大小是1G； 

RocketMQ 同时会生成 ConsumerQueue , 中间会以主题创建文件夹，每个主题根据创建的文件会在主题下有index为名称的文件夹

该文件夹下存放一个类似于索引的文件

RocketMQ 将不同主题的队列的数据 commitLog中的偏移量， 数据大小 以及 tag的hashcode 存放在索引文件中，当然生成索引的

过程是异步的。



为什么两种MQ的设计不同，主要是针对的场景不同， Kafka 设计之初是面向大数据的，所以将一个partition 分为一个文件，这样，整个

kafka承载的数据量就会比较大。

但是RocketMQ 的设计之初是面向电商，在电商中，会有大量topic， 每个topic 中可能有很多的queue, 如果还是按照kafka的文件规则，那

么意味着会有非常多的文件，一个请求可能要写入非常多的文件，效率低，并且每个文件可能都不大，也不科学。

### 9. 零拷贝

> 什么是零拷贝

是一类技术：主要目的是减少没有必要的拷贝。为了减少IO

需求：读取本地内容，然后通过网络将数据发送给服务端

上面这个需求需要四次拷贝：

1. 先把数据从磁盘读取到操作系统中的文件读取缓冲区   DMA拷贝
2. 从文件缓冲区中 拷贝到 应用程序的内存中  CPU 拷贝
3. 通过网络发送，从应用程序中拷贝到 Socket 缓冲区 CPU 拷贝
4. 从Socket缓冲区 发送到网络另一端  DMA 拷贝

DMA 拷贝比较快， CPU 拷贝相对比较慢



> 实现零拷贝的方式

* 操作系统中有个虚拟内存技术，本质就是就是把硬盘当内存使用

  * 基于上面的技术，我们可以将操作系统的文件读取缓冲区舍弃， 如果我们使用的磁盘刚好是被用到的操作系统的内存

    那么就可以减少一次拷贝，但是应用程序想要知道用哪块磁盘去做内存映射，需要用到一个技术 MMAP

  * 同样的，Socket 缓冲区也可以被这种技术代替

  * 使用这样的方式，两次CPU拷贝都可以被舍弃

  * Java 中的 NIO channel.map() 其实就是使用了MMAP的技术



> RocketMQ && kafka 怎么实现

kafka:

sendfile()  通过发送文件描述符的方式， 让数据从文件读取缓冲区 直接 发送到 套接字缓冲区，从而减少两次CPU拷贝



rocketMQ:

通过nio 减少了一次 CPU 拷贝，数据还是要走应用内存，从速度上来说肯定是不如kafka，但是可以实现很多功能
