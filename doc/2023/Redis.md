### 2. Redis 持久化

> 持久化方式有哪些

* RDB   redis database 使用快照的方式将内存数据在某一时刻记录到磁盘
* AOF   append only file 将所有执行的写操作追加到文件中，查询操作不会记录
* RDB-AOF 混合持久化

> 持久化方式的优劣

* RDB
  * 速度很快，并且因为生成的问题是二进制文件，所以文件大小也比较小
  * 但是会造成数据丢失，在RDB间隔时间的数据会丢失
* AOF
  * 持久化保证实时，一般的我们是1秒进行1次AOF，所以最坏我们丢失1s的数据
  * AOF的文件比RDB文件要大的多，恢复的时候因为要一条条的执行命令，恢复数据的速度也会比较慢
    * 如果通过AOF恢复，那么Redis启动的时候也会比较慢

### 3. Redis 的事务

> Redis 怎么开启事务

使用 multi 开启事务，使用exec结束事务并提交，中间是事务的执行命令。

> Redis 事务执行的基本流程

Redis执行事务，本质上就是将事务中的命令先缓存到队列中，然后在提交的时候一次执行。

> Redis 事务的优劣

Redis 的事务是弱事务，是不可靠的事务。

Redis的事务回滚只能对错误的语法感应，但是这种感应只能发生在错误的语法之后。

* 当错误的语法发生的时候，回滚只发生在错误的语法之后，如果事务中错误的语法之前的动作会成功提交

### 5. Redis 不常用的数据类型

* HyperLogLog

> 统计高并发网站的 UV 数据如何实现

UV : unique view  需要对数据进行去重， 比如一个直播，你想看到有多少用户看过，那么有可能一个用户访问了多次，所以我们不能简单的通过计数器做自增，我们需要对用户进行去重

PV :  PV的数据就比较简单，我们常见的直播的热度其实就是PV，做个简单的计数器统计数据即可。

统计UV  key  value 其实也能实现，比如统计每天的网站数据   set  2020-01-02-user1 1  

使用上面的方式当然可以，但是当你的用户增长的一定给的程度之后，内存的消耗肯定是扛不住的。

使用 HyperLogLog是基于概率的， 官方的误差率是0.81%，但是占用的内存非常小

```redis
pfadd u-2-22 user1 user2 user3 ... # 添加元素

pfcount u-2-22  # 统计元素个数

pfmerge u-2-21 u-2-22 # 可以将多个数据进行merge
```

使用上面的方式添加元素，看起来是添加了很多，但是其实占用的存储空间很小

> hyperLogLog的原理

* 伯努利试验
* 极大似然算法
* 分桶优化

### 6. Redis Key Value 数据结构

全局哈希表

类似于 hashMap , 底层还是数组

![image-20230619101802328](C:\Users\86183\AppData\Roaming\Typora\typora-user-images\image-20230619101802328.png)

理解上面的图， 最基层的数据结构是数组，数组的每个 index下存放的又是一个链表，每个元素是 Entry， Key是String 类型， value 则是我们常见的数据类型，

但是和hashMap不同的是 Redis 的全局哈希表是没有红黑树的。

虽然使用哈希表能让查询的时间复杂度是 O(1) 但是上面的结构就存在一个问题：

* 哈希冲突

随着哈希冲突的增多，那么链表的长度肯定会变长，使查询效率变低，redis解决这个问题的方案也很简单，那就是数组扩容，只要数组的容量足够大，那么发生哈希冲突的概率也会比较小，自然链表的长度就不会很长。但是数组扩容会带来一个问题，在进行数组扩容的时候，是阻塞查询的。



> 什么是渐进式 rehash

redis 扩容会面临一个问题： 中间存储的元素的 rehash， 扩容的时候不能查询中间态，所以普通哈希会阻塞IO

redis 使用渐进式 rehash 的方式解决 rehash的阻塞问题

* redis  会初始两张hash表，但是只有一张hash表投入使用 -- 哈希表1
* 当 哈希表1 需要扩容的时候， 不是直接扩容哈希表1， 而是将哈希表2 扩容
* 当有客户端请求过来的时候，除了从老的哈希表中1查询数据，还会将对应查询的数组 index 下标的链表进行 rehash到新哈希表2
  * 这个过程非常短，因为一个链表的数据肯定不会很多
* redis会记录 rehash的数据，当再有用户查询的时候，会判断数据是否已经rehash从而判断在哈希表1查询还是哈希表2查询
* 随着用户进程的不断进行，哈希表1上的数据也会不断被重新 rehash 到哈希表2 上从而实现数据扩容

### 7. Redis 分布式锁

* setnx 可以实现互斥的操作
* 如果 setnx的服务挂了，可能会造成锁无法释放的问题
  * expire 设置锁的超时时间
* 加锁 + 设置过期时间 两个命令不是原子性的
  * 通过 set  ex nx 一个命令可以做到原子性
* 服务1 加的锁如果被 别的服务 解锁了
  * 通过 key 的关键字来解决这个问题，比如商品加锁   set goods-1 uuid ex 10 nx
  * 程序通过 key 拿到 value 做个判断，不是自己加锁不能释放锁
* 释放锁的时候 ，需要先get value 做判断然后再释放，又不是一个原子命令了
  * 使用lua脚本保证原子性
* 锁的过期时间不好控制，因为我们没法判断业务的执行时间
  * 加一个看门狗线程 ，这个线程是一个守护线程，随着加锁线程的产生而产生，当然也会随着加锁线程的结束而结束
  * 这个守护线程中定时监测，如果锁即将失效，但是业务还在执行，那么我们这个线程会对锁进行一个续期
* 一个线程可能加很多个锁，每个锁的失效时间不同
  * 看门狗线程中加入一个延时队列，通过延时队列的take() 让锁在释放之前一点点时间执行续时操作，避免一个人带着“一群狗”的情况
  * redission 已经实现了看门狗，不用我们手写了

### 9. 缓存穿透

查询根本不存在的数据， 缓存层和存储层都不会命中，压力全部给到了数据库，一般是被人攻击导致的。

解决方案：

* 对数据进行校验，比如id校验合法之类的
* 布隆过滤器中校验数据库中有没有数据，如果没有数据，请求压根就不给到数据库
* 缓存空对象， 将请求到数据库中没查到的数据在redis中缓存一个null

### 10. 缓存雪崩

大面积的key失效导致的 大量请求全部作用于 数据库上的现象，一般如果缓存宕机，阻塞之类的导致出现这个问题

解决方案：

* redis 不是单节点  主从 + 哨兵 / 集群  --- 在分布式架构中，避免单点故障
* 隔离组件  进行限流 降级 
* 设置失效时间的时候随机，让失效的key均匀的失效，防止出现大面积的key集中失效

### 12. 热点 Key

访问量很大的key， 热点新闻等

造成的问题：流量不均衡，比如一个redis集群中， 因为热点key的情况，可能会导致其中几台机器访问量暴增，压力变大，而其他的机器空闲

查找热点key：

* redis 端的监控命令  monitor 
  * 但是这个命令肯定是有开销的，短时间内可以用，长时间不推荐这么用
* FaceBook 开源的工具 redis-faina 也是基于上面的命令的
* 通过客户端的 --hotKeys 用于查找热点key
  * 但是这个命令受限于内存淘汰策略

解决方案：

* 使用二级缓存，将热点key放在 hashmap, ehcache等中，我们程序直接进行处理
* 进行key的分散 将热点key放到不同的机器上进行负载均衡

### 13. redis 过期策略

> redis 过期策略都有哪些

配置项： maxmemory-policy

* 默认值： noeviction  不会继续写，但是可以读，数据不会丢失
* volatile-lru 尝试淘汰设置过期时间的key , 淘汰的方式是lru 
* volatile-ttl  尝试淘汰设置了过期时间的key, 根据TTL的时间
* volatile-random 随机淘汰设置了过期时间的key
* allkeys-random  随机淘汰所有的key
* allkeys-lru 使用lru策略淘汰所有的key



> 了解 LRU 算法吗

LRU least recently used 最近最少使用

最长见的是链表实现，被访问的元素放在头节点，那么链表尾节点就是使用最少的元素

Redis 中 LRU的实现：

在每个key增加了一个额外的字段 24 bit 的时间戳，记录最后一次访问的时间

当触发LRU的时候，触发随机采样，淘汰采样中的最旧的那个，这个采用率，使用 maxmemory-sample参数控制

Redis 3.0 之后实现了一个淘汰池，池中始终是最小时间的元素，每次往池中放元素的时候会做时间比较，保证池中的数据是最老的

### 14. 缓存一致性问题

按照写入顺序分为以下几种：

* 先更新数据库，再更新缓存

这个方案有问题，如果数据库更新成功，缓存更新失败，那么会导致数据的不一致，且这个不一致不容易被发现

这种方式在并发下也会出现问题：

​	线程A 和线程B 都需要更新，原来的顺序是线程A 先更新数据库，线程B 再更新数据库， 线程A 更新缓存，线程B再更新缓存，但是因为网络问题，导致，线程A在更新缓存的时候落后于线程B, 这样就出现了脏数据

* 先更新缓存，再更新数据库

这个方案我们一般不用，因为如果更新缓存成功，更新数据库失败，就会出现不一致，且很难察觉不一致

* 先删除缓存，再更新数据库

这种方案会产生问题：

线程 A 是一个更新线程，线程B 是一个读取操作， 多线程情况下，线程A 先删除缓存， 在还没有更新数据库的时候，线程B查询数据，线程B先去redis种差不到数据，因为数据已经被线程A删了，那么线程B就会去数据库种读取数据，但是此时A还没完成对数据的更新，线程B读到了老数据，并将老数据放到了缓存中。造成了数据不一致的情况。

解决方案：

采用双删策略， A 删除缓存， 更新数据库， 再删除缓存，确保下次读取会读取到最新的数据，保证数据的一致性，当然，第二次删除前要休眠一点点时间

* 先更新数据库，再删除缓存

这种方式被称为 cache Aside pattern， 是一种比较好的方式

生产环境中一般是这种方案 + 延迟双删
